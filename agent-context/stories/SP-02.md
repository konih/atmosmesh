# SP-02 — AtmosMesh Spot firmware: C3 product environment and composition root

- **Status:** In flight (first image flashed and running on the soldered unit, 5 September 2026)
- **Priority:** P3
- **Milestone:** Spot v1
- **Depends on:** SP-01 (carrier design, soldered 4–5 September 2026)

## User story

As the operator, I want the soldered Spot carrier to run a real AtmosMesh product image — every
sensor read, the little OLED useful, readings in Home Assistant under its own station id — so
that the node goes from "soldered and tested" to "in a room" without a bring-up sketch.

## Outcome

One PlatformIO environment `atmosmesh-spot-v1` (ESP32-C3, Arduino core 3.x, native USB console)
and one composition root `firmware/src/products/atmosmesh_spot_v1.cpp` that:

- reads the SHT41 (raw I²C, host-tested CRC), the VEML7700 (fixed gain, no-wait read), the DS18B20 probe
  (1-Wire, powered mode, non-blocking conversion, re-discovered when unplugged and re-plugged),
  and the HLK-LD2410S (presence on `OT2` through a debounce and hold; distance and the raw target
  state from the UART report, decoded by a host-tested stream parser);
- publishes on the shared MQTT contract as `atmosmesh-spot-0001` with Home Assistant discovery:
  `temperature_c`, `humidity_pct`, `illuminance_lx`, `probe_temperature_c`,
  `presence_distance_cm`, `presence_state`, `wifi_rssi_dbm`, and the `presence` occupancy
  binary sensor — each `{value, unit, valid, age_ms}` so an unplugged breakout goes unavailable;
- drives the 72 × 40 OLED: one value per page, rotating every 3 s, BOOT button forces the next
  page, presence glyph top-right and link state bottom-right on every page;
- limits Wi-Fi TX power to 8.5 dBm at start-up (SuperMini antenna) and logs RSSI every 5 s;
- logs every stage on the USB console so a wiring fault names itself.

## In scope

- Environment, composition root, `spot_pins.hpp` with static-asserted pin map, LD2410S frame
  decoder, presence hold, the contract-parametrised `esp32_mqtt_runtime`, host tests, Taskfile
  entries, README section.

## Out of scope

- Switching the radar to its standard (per-gate energy) output mode — SP-04.
- Moving the Room image onto `esp32_mqtt_runtime` (it keeps its own file until this one has run
  for a while).
- A second unit or per-room station ids — SP-05.

## Acceptance criteria

- [x] Given the environment, when `pio run -e atmosmesh-spot-v1` runs, then it builds on the
      espressif32 7.x / Arduino core 3.x toolchain. **5 September:** RAM 12.6 %, flash 72.5 %.
- [x] Given `pio test -e native`, then the LD2410S decoder, presence hold and Spot contract
      tests pass alongside the existing ones. **169 cases** (ACK parsing and command builder
      added with the handshake).
- [x] Given the soldered unit, when the image boots, then the log shows the hello with product
      and station id, the bus scan with `0x10 0x3C 0x44`, and every sensor's presence.
- [x] Given the sensors, then SHT41, VEML7700 and DS18B20 readings appear in the 5 s log line
      and reach the broker (`mqtt: connected`, state on `home/air/atmosmesh-spot-0001/state`).
- [x] Given the radar's `OT2`, then presence flips in the log and on the display.
- [x] Given the radar's UART on the RX pin, then frames arrive and `presence_distance_cm` is
      valid. **5 September, 03:30:** continuous stream at 3–4 frames/s after the boot kick,
      `<- ack end-config status=0`; distance and state on the display and in the payload.
- [ ] Given Home Assistant, then the eight entities appear under "AtmosMesh Spot 0001" and go
      unavailable when their sensor is pulled (operator check).
- [ ] Given the OLED, then the pages read correctly with the module in its socket, or
      `ATMOSMESH_SPOT_OLED_ROTATION` is set (operator check).

## Validation

- Automated: `pio test -e native` (frame decoder including resync and look-alike bytes,
  presence debounce/hold, Spot contract, discovery count and templates, session replay).
- Manual: serial log on `/dev/ttyACM0`; broker check; OLED pages; radar presence with a person
  still and with the room empty.
- Failure/edge case: I²C line held low refuses to start the drivers and says which line; a
  probe unplugged goes unavailable after three bad scratchpads and is found again when plugged
  in; a radar with a silent UART still yields presence from `OT2` but never a distance.

## Evidence

- 2026-09-05 01:15 — soldering check with `firmware/tools/c3scan` on the finished carrier:
  `SDA=GPIO5 SCL=GPIO6 -> 0x10 (VEML7700), 0x3C (OLED), 0x44 (SHT4x)`, nothing else on any pair.
- 2026-09-05 01:30 — first product image: boot log correct up to the sensors, then both I²C
  sensors stopped answering and `oled.begin()` never returned. Bisected by sampling the sensors
  before and after the OLED init: fine before, gone after. Cause: U8g2 constructed with the pin
  numbers calls `pinMode()` on SDA/SCL in its GPIO init, and on Arduino core 3.x the peripheral
  manager hands those pins back from the I²C driver. Fix: construct U8g2 without pins; Wire is
  started by the bus scan. Recorded in the source and in `firmware/README.md`.
- 2026-09-05 01:40 — full run: `t=27.7C rh=61% lux=29 probe=24.9C presence=occupied`, Wi-Fi at
  −72 dBm on channel 11 with the 8.5 dBm limit applied, `mqtt: connected` as
  `atmosmesh-spot-0001`, slowest loop stage the VEML7700 auto-ranging read (300–720 ms in the
  dark). The SHT41 reads about 3 K above the probe and climbs over minutes: board self-heating
  next to the SuperMini's LDO and the radar — the Room comparison criterion in SP-01 will need
  the sensor on a lead or the number explained.
- 2026-09-05 01:50 — radar UART: `OT2` is high and presence works; the RX pin (GPIO20) idles
  LOW against a pull-down and 0 bytes arrive in 40 s; GPIO21 idles LOW too, so `OT1` is not on
  the TX pin either. Operator confirms the wiring matches the drawing with nothing in series.
- 2026-09-05 02:05 — pin-edge probe (throwaway sketch, interrupts on GPIO 0, 1, 2, 7, 10, 20,
  21 and 3): no edge on any free pin in 8 s with pull-downs nor 8 s with pull-ups; GPIO20 reads
  0 then 1, i.e. it floats; GPIO3 (`OT2`) reads 1 throughout. Enable-config + read-version sent
  on TX=21/RX=20 and again crossed: no ACK either way. Operator confirms GPIO20 (RX) → `OT1`
  and GPIO21 (TX) → radar `RX`. Conclusion: the `OT1` path is open — a joint, or the module's
  header pin — not a pin-mapping or firmware issue. Meter check is the next step; the product
  image is back on the board and runs on `OT2` meanwhile.
- 2026-09-05 02:20 — operator's scope: `OT1` flat, only the C3's `TX` high. Hi-Link's Operation
  Guide (filed in `docs/hardware/datasheets/`) confirms continuous default reporting and names
  the enable-configuration reply as the health check, which this module fails. Its wiring photo
  shows series link footprints next to the `OT1`/`RX` pins; an open link in the `OT1` position
  is the leading explanation. See SP-01 Evidence for the meter steps.
- 2026-09-05 02:40 — **operator reflowed the module's chip.** First boot after: 18 bytes on
  GPIO20, `FD FC FB FA 08 00 FF 01 00 00 03 00 80 00 04 03 02 01` — the enable-config ACK — then
  one minimal frame, then silence; every later reset the same 18 bytes and nothing else. So the
  transmitter worked, and something at reset (the ROM/bootloader lines on the C3's TX) read as
  a command to the module.
- 2026-09-05 02:55 — handshake firmware (break, enable, read-version, output-mode, end; every ACK
  logged): frames for the first 2 s after reset, then silence, with Wi-Fi on or off; five full
  command sequences unanswered; breaks of 200 ms and 1.5 s alone unanswered.
- 2026-09-05 03:10 — **cause found: the C3's pull-down on GPIO20.** The boot wiring check set
  `INPUT_PULLDOWN` on the RX pin; `Serial0.begin()` attaches UART0 RX through the direct mux and
  leaves the pull as is. The module's `OT1` is a weak driver: LOW against that pull-down, HIGH
  against a pull-up. With `GPIO_PULLUP_ONLY` after `begin()`: continuous frames (496 in 150 s),
  enable-config ACK to each command. The 2 s of frames after every reset were the window before
  `pinMode()` ran. Also seen: the loop's slowest stage was the VEML7700 auto-range read at 5.1 s
  in the dark (fixed gain 1/4, no-wait read now; slowest stage 43 ms), and a spontaneous
  enable-config ACK every ~34 s while esp-mqtt retried — IDF logs on UART0 (silenced).
- 2026-09-05 03:30 — final image: boot kick = break + end-config → `<- ack end-config (0xFE)
  status=0 uptime=3s`, `reporting (22 frame(s)); handshake done`, 3–4 frames/s for the whole
  capture, `radar=71cm/s2` on the 5 s line. Wi-Fi did not associate in the last two runs
  (−90 dBm at the bench in the run before); not a Spot fault, retry logic unchanged.

## Notes

- Station id follows the existing product pattern (`atmosmesh-room-0001` → `atmosmesh-spot-0001`)
  rather than SP-01's earlier "atmosmesh-0004 upward" wording; SP-01 is updated.
- `presence_state` is the radar's raw byte (0/1 nobody, 2/3 somebody). The manual gives no finer
  meaning, so the firmware publishes the number and does not label it moving/still.
